# Adversarial QA — Fresko Container + Fresko Deal
Date: 15 Sep 2026
Source: FRESKO_UNIVERSE_CODEX_START_HERE.md (proposed DocTypes §7, lifecycle §8, approval §9, stock §10, WhatsApp §11, alias §16, exceptions §21, open questions §35)

## Summary

The proposed Fresko Container and Fresko Deal DocTypes state the right principles (idempotent WhatsApp ingestion, no silent edits, stock checks before approval, unresolved-buyer hold, fail-closed close), but leave several control surfaces unspecified at design level. Highest-severity holes: (1) `source_message_id` / `duplicate_fingerprint` uniqueness and forwarded-copy semantics are named but not constrained, so the same commercial order can double-count as two Deals; (2) stock availability is checked as a rule, yet reservation semantics for approved-but-not-dispatched qty are an open question (§35), enabling TOCTOU over-approval and unreconciled closes; (3) `approved_rate` can be overwritten without a mandatory Fresko Approval revision trail if Desk edits are not blocked; (4) Container carries only aggregate `inward_qty` with no lot-level inward child table, so “wrong container for lot” and lot overdraw cannot be enforced deterministically; (5) buyer alias can remain unresolved while Deal progresses commercially, and remap after posting has no revision contract. Together these allow double-counting, silent rate/qty mutation, and container closes that do not reconcile inward vs sold/outward/pending/cancelled/unsold.

## Attack matrix

### 1. Duplicate WhatsApp orders (same message_id / fingerprint / forwarded copy)
**Break attempt:** Agent forwards Rehan’s original WhatsApp “Rehan 50 crate 41869 600” (Meta `message_id=wamid.AAA`) into the Fresko ops group. Webhook delivers the same event twice (retry). Separately, another agent pastes the same text as a new chat message (`message_id=wamid.BBB`, different content hash of the wrapper but identical commercial body). Parser creates Deal A from the first delivery, Deal B from the retry (if idempotency key is only loosely applied), and Deal C from the forwarded copy. Container approved_sold becomes 150 crates against one real 50-crate commercial intent; settlement certificate shows inflated gross sales.
**Expected fail-closed behavior:** Persist WhatsApp message ID, sender, timestamp, attachment IDs, content hash, and ingestion status (§11). Same `message_id` must never create a second financial event (reject ingest as already processed). Same commercial `duplicate_fingerprint` (normalized buyer+lot+qty+rate+unit+container scope, or content hash of body) must either link to the existing Deal or open a held exception—never AUTO_APPROVE a second Deal. Forwarded/internal copies with new `message_id` but matching fingerprint must be treated as duplicate evidence attached to the original Deal, not a new Deal.
**Exception / state:** `DUPLICATE_MESSAGE`; Deal remains single instance in `PROPOSED` / `APPROVAL_REQUIRED` / `APPROVED` (whichever already exists); duplicate ingestions stay as Fresko Evidence linked to that Deal with ingestion status = duplicate/ignored; no second Deal in any non-cancelled financial path.
**Minimum automated test:** `test_duplicate_whatsapp_message_id_and_fingerprint_do_not_create_second_deal` — assert one Deal for `wamid.AAA` retries and for a forwarded body matching `duplicate_fingerprint`, with `DUPLICATE_MESSAGE` exception and zero second `approved_sold` qty.
**Design gap today:** Fresko Deal lists `source_message_id` and `duplicate_fingerprint` (§7) and §11 requires persistence of message ID / content hash / “never create a second financial event,” but the brief does not specify unique indexes, fingerprint algorithm (what fields, normalization, container scope), whether fingerprint uniqueness is hard-unique vs soft-exception, how forwarded copies with new Meta IDs are classified, or whether Evidence.sha256 alone is enough when the chat wrapper differs. Open questions do not close this.

### 2. Insufficient lot stock
**Break attempt:** Lot 41869 has 80 crates physical inward remaining available_to_sell. Salesperson A submits “Rehan 50 crate 41869 650”; salesperson B simultaneously submits “Morya 50 crate 41869 660”. Both pass the “sufficient available quantity” check (§9) against the same pre-reservation snapshot. Both become APPROVED / AUTO_APPROVED. Approved sold = 100 against 80 inward; later physical outward cannot cover both; container close arithmetic disagrees (inward vs approved_sold vs outward).
**Expected fail-closed behavior:** Deterministic stock rule must refuse approval (or refuse transition to APPROVED / AUTO_APPROVED / OUTWARD_PENDING) when requested qty exceeds available_to_sell for that lot+container, after accounting for already approved and reserved qty. Concurrent submissions must serialize on lot stock (or use atomic reservation) so the second fails closed. Exception when an approved deal would exceed available stock (§10).
**Exception / state:** `QTY_EXCEEDS_AVAILABLE_STOCK` (and/or `LOT_OVERDRAWN` if lot inward is exceeded); second Deal held at `PROPOSED` / `APPROVAL_REQUIRED` with reject-or-hold, or rejected; must not reach `APPROVED` consuming unavailable stock. Container close blocked while unresolved.
**Minimum automated test:** `test_concurrent_deals_cannot_over_approve_lot_available_stock` — assert only one of two 50-crate approvals succeeds against 80 available, other gets `QTY_EXCEEDS_AVAILABLE_STOCK` and no approved qty increment.
**Design gap today:** §9 lists “Is sufficient available quantity present?” and §10 lists exception `approved deal exceeds available stock`, but §35 explicitly leaves “Exact stock reservation semantics for an approved but not dispatched deal” undecided. Fresko Container has only aggregate `inward_qty`—no lot-level inward / reserved / available fields on the DocType sketch. No reservation child table, no locking/serialization contract, no definition of whether PROPOSED qty reserves stock.

### 3. Wrong container for a lot
**Break attempt:** Container FPL-PLUM-03 owns lot 41869. Agent texts “Rehan 50 crate 41869 650” while the ops thread or UI context is Container FPL-PLUM-02 (different arrival). Parser binds Deal to FPL-PLUM-02 because container was inferred from chat context, not from lot master. Deal approves against the wrong container’s stock and settlement; lot 41869 never appears correctly on FPL-PLUM-03’s commercial ledger; close of both containers can look “reconciled” while physical lots are mis-attributed.
**Expected fail-closed behavior:** Rule “Is the lot valid for this container?” (§9) must be hard: lot→container membership is authoritative. If lot 41869 is not registered to the Deal’s container, reject creation/approval (or force correction) before any APPROVED state. Do not allow free-text lot strings that are not linked to a Container lot/batch identity. Preserve commercial LOT No. even if ERPNext batch ID differs (§10), but membership must still resolve.
**Exception / state:** Design should treat as hard reject or a dedicated hold; closest listed type is `LOT_OVERDRAWN` / stock exceptions, but a lot-not-on-container mismatch should fail before stock math—Deal must not leave `PROPOSED` as APPROVED on the wrong container. Prefer explicit exception (not listed verbatim in §21) or map to validation failure + `MANUAL_OVERRIDE` only if an authorized override with evidence is used. Container status must not count the qty in approved_sold for the wrong container.
**Minimum automated test:** `test_deal_rejects_when_lot_not_registered_on_deal_container` — assert Deal for lot 41869 on container FPL-PLUM-02 is rejected/held and approved_sold on FPL-PLUM-02 does not increase.
**Design gap today:** Fresko Deal has `container` and `lot/batch` fields (§7) and §9 asks validity, but there is no Lot child DocType/table under Container, no uniqueness of lot within/across containers, and no specified join key between commercial LOT No. and ERPNext Batch. Wrong-container binding is therefore a parser/UI inference risk with no schema-enforced membership.

### 4. Changed sale rate after approval
**Break attempt:** Deal for Rehan 50 crates lot 41869 is APPROVED at `approved_rate=650` with Fresko Approval decision_rate=650. Later, in Desk, someone edits `approved_rate` to 600 (or overwrites `proposed_rate`) to match a verbal discount, without creating a new Fresko Approval or revision row. Partner settlement and gross_sales use 600; audit cannot show old_value/new_value/approver for the commercial change. Same break via API PATCH on Fresko Deal bypassing `fresko.approvals.decide`.
**Expected fail-closed behavior:** “Never silently mutate an approved financial record” (§0, §3.3). Human approval must write an immutable Fresko Approval record; do not merely overwrite `proposed_rate` (§9). Post-approval rate change must create a revision preserving old_value, new_value, changed_by, changed_at, reason, supporting_evidence, approval_reference; financially material change requires a new Approval decision. §10: exception when a transaction is edited after dispatch without revision/approval; §21 lists `RATE_CHANGED_AFTER_APPROVAL`.
**Exception / state:** `RATE_CHANGED_AFTER_APPROVAL` (and `MANUAL_OVERRIDE` if Desk force-edit attempted); Deal stays at prior approved commercial values until a new Approval revises them; if edit detected after `DISPATCHED`, Deal may enter `DISPUTED` / hold pending resolution. Container settlement must not silently adopt the overwritten rate.
**Minimum automated test:** `test_post_approval_rate_edit_creates_revision_and_rate_changed_exception` — assert direct write to `approved_rate` after APPROVED is rejected or produces immutable revision + `RATE_CHANGED_AFTER_APPROVAL`, and gross_sales still uses pre-change rate until re-approved.
**Design gap today:** Fresko Deal stores both `proposed_rate` and `approved_rate` on the same document (§7) with no stated field-level write protection, no mandatory link that `approved_rate` may only change via Fresko Approval.decision_rate, and no revision child table in the DocType sketch. Principle §3.3 is clear; the DocType design does not encode it. Desk status/field edits bypassing the state machine are warned against in §8 but not field-scoped for rates.

### 5. Unresolved buyer alias
**Break attempt:** Message “AZ/SSK 40 crate 41871 700” creates Deal with `unresolved_buyer_alias=AZ/SSK` and empty/null `customer`. System AUTO_APPROVES on rate band and stock, dispatches, and books receivable against a null or placeholder party. Later alias is confirmed to SSK Fresh Fruit Pvt Ltd—or worse, remapped to a different Customer—after deals are posted; party ledger and partner settlement attribute cash to the wrong legal buyer. Duplicate aliases (Rehan / Rehaan) create two Customer trajectories for one counterparty.
**Expected fail-closed behavior:** Alias engine must produce candidates, not blindly rename (§16). Financial progression that needs a Customer (approval beyond provisional, dispatch linkage to party ledger, payment match, settlement) must require confirmed Customer or an explicit authorized override. Unresolved alias → exception and hold. Never destroy original alias string. Remap after posting must be revision-oriented with evidence, not silent Customer rewrite on historical Deals.
**Exception / state:** `BUYER_UNRESOLVED`; Deal should remain `PROPOSED` / `APPROVAL_REQUIRED` (or a non-final commercial state) until Customer confirmed—or APPROVED only with explicit policy + exception still open. Container Settlement `unresolved_exception_count` must include open `BUYER_UNRESOLVED`; container must not appear fully reconciled (§18).
**Minimum automated test:** `test_unresolved_buyer_alias_blocks_final_commercial_posting` — assert Deal with only `AZ/SSK` and no confirmed Customer cannot reach RECONCILED / settlement inclusion without `BUYER_UNRESOLVED` open, and remapping Customer after APPROVED writes revision history.
**Design gap today:** Fresko Deal allows `customer / unresolved_buyer_alias` as alternatives (§7). Fresko Buyer Alias / Candidate DocTypes exist (§7, §16), and `BUYER_UNRESOLVED` is listed (§21), but the brief does not specify which Deal statuses are illegal while alias is unresolved, whether AUTO_APPROVE is allowed without Customer, or the remap contract for historical deals. §35 leaves final public buyer identity mappings open—design must not treat confirmation as a silent backfill.

### 6. Partial dispatch
**Break attempt:** Approved Deal: Rehan 50 crates lot 41869. Cold storage outward/gatepass records 30 crates only. Ops marks Deal `DISPATCHED` (full) anyway, or leaves status `APPROVED`/`OUTWARD_PENDING` while physical_outward=30 with no split. Later another gatepass of 20 is entered without Deal link (`OUTWARD_WITHOUT_DEAL`), or the remaining 20 is never dispatched and container close treats all 50 as sold/dispatched. Alternatively Deal is set `PARTIALLY_DISPATCHED` in Desk without child dispatch lines summing to 30, so pending_outward and physical_outward diverge.
**Expected fail-closed behavior:** State machine (§8) includes `PARTIALLY_DISPATCHED` and path APPROVED → OUTWARD_PENDING → DISPATCHED. Physical outward must link to Deal ID; quantity rules: exception when physical outward exists with no approved Deal, when outward qty exceeds approved without explicit split/adjustment, and when deal remains without outward (§10, §21: `OUTWARD_WITHOUT_DEAL`, `DEAL_WITHOUT_OUTWARD`). Partial dispatch must keep Deal in `PARTIALLY_DISPATCHED` / `OUTWARD_PENDING` with pending_outward = approved − linked outward, not jump to full `DISPATCHED`. Container snapshot must show approved_sold, physical_outward, pending_outward distinctly (§2, §10, §27).
**Exception / state:** `DEAL_WITHOUT_OUTWARD` (remaining 20), and/or `OUTWARD_WITHOUT_DEAL` if orphan gatepass; Deal status `PARTIALLY_DISPATCHED` or `OUTWARD_PENDING` until linked outward sums to approved (or explicit cancel/adjustment). Container close with mismatch → `CONTAINER_QTY_NOT_RECONCILED`.
**Minimum automated test:** `test_partial_outward_keeps_deal_partially_dispatched_and_pending_qty` — assert 30/50 outward leaves Deal `PARTIALLY_DISPATCHED`, pending_outward=20, no full DISPATCHED, and orphan 20-crate gatepass raises `OUTWARD_WITHOUT_DEAL`.
**Design gap today:** Lifecycle names `PARTIALLY_DISPATCHED` (§8) and Container Settlement has pending_outward / approved_sold fields (§7), but Fresko Deal DocType sketch has no dispatch child table, no linked outward qty fields, and no rule that status DISPATCHED is only legal when sum(linked outward) == approved qty (or approved − cancelled). Gatepass conflict rule is stated narratively (§10) without DocType fields for gatepass status vs movement.

## Residual breaks the DocType design still allows

- **Concurrent stock TOCTOU:** Availability check without atomic reservation (§35 open) allows two APPROVED deals to pass the same available_to_sell snapshot; unique constraints on Deal do not serialize lot stock.
- **Lot-level inward missing on Container:** Container DocType lists aggregate `inward_qty` only (§7); no lot/count inward child table, so lot inward vs lot outward (`LOT_OVERDRAWN`) and “lot valid for container” cannot be enforced from schema alone.
- **Desk status edits bypassing state machine:** §8 says transitions must be validated in code and arbitrary UI edits to impossible states disallowed, but DocType `status` is a plain field—without server-side transition guards and restricted Desk permissions, users can set DISPATCHED, PAID, or RECONCILED directly.
- **Settlement snapshot drift:** Fresko Container Settlement is a field bag (inward, sold, outward, collections, expenses, receivable, unresolved_exception_count) (§7, §18) with no stated immutability after `closed_at`, no link that close is blocked when `unresolved_exception_count > 0` for material types, and no versioning if underlying deals/payments change after certificate generation (`SETTLEMENT_VALUE_MISMATCH` risk).
- **Alias remap after deals posted:** Confirmed mapping AZ/SSK → Customer X can later be “corrected” to Customer Y; Deal.customer overwrite without revision rewrites party ledger history; brief forbids destroying original alias but does not forbid silent Customer FK changes on posted Deals.
- **Container close with open exceptions:** §18 says a container with unresolved material exceptions should not appear fully reconciled, and §10 says close must reconcile to inward—but Container `closing_status` / Settlement close path is not specified as fail-closed against open `DUPLICATE_MESSAGE`, `QTY_EXCEEDS_AVAILABLE_STOCK`, `BUYER_UNRESOLVED`, `OUTWARD_WITHOUT_DEAL`, etc.
- **Fingerprint vs message_id asymmetry:** Retries of same `message_id` are covered in intent; commercially identical forwards with new IDs depend on unspecified `duplicate_fingerprint`—residual double-count if fingerprint is optional or non-unique.
- **Proposed vs approved qty mutation:** Same silent-edit hole as rate—qty on an APPROVED Deal can be edited in Desk without revision, breaking stock and settlement without necessarily firing `RATE_CHANGED_AFTER_APPROVAL`.
- **Payment screenshot ≠ verified:** Adjacent to Deal lifecycle (PAYMENT_PENDING → PAID): WhatsApp payment evidence can advance Deal to PAID if states are not gated on payment VERIFIED/CLEARED (§19)—inflates reconciled collections at container close.
- **Hold gatepass vs later physical movement:** §10 lists gatepass status conflicts; no DocType field for gatepass hold state on Deal/dispatch link, so conflict detection is unspecified.

## Recommendations for Architecture / Frappe (non-implementing)

1. **Idempotency uniqueness:** Mandate DB-unique `Evidence.message_id` (nullable only for non-WhatsApp) and a defined, indexed `Deal.duplicate_fingerprint` (normalized container+lot+qty+rate+unit+buyer_alias+event_date window, or body content hash). Same message_id → ingest no-op; same fingerprint → attach Evidence + `DUPLICATE_MESSAGE`, never second Deal.
2. **Lot child table under Fresko Container:** Require lot_id / commercial LOT No., inward_qty, unit, optional ERPNext batch link; Deal.lot must FK to a lot row on Deal.container. Reject deals whose lot is not on that container.
3. **Stock reservation semantics (decide §35 before Phase 1):** Define whether PROPOSED and/or APPROVED qty reserves available_to_sell; implement atomic reserve-on-approve (row lock or reservation ledger child table) so concurrent approvals cannot double-consume; release on CANCELLED / reject.
4. **Approval-owned commercial fields:** `approved_rate` and approved qty may change only via Fresko Approval (or explicit revision DocType) with old/new/actor/time/reason/evidence; block Desk/API direct writes after APPROVED; emit `RATE_CHANGED_AFTER_APPROVAL` on violation attempts.
5. **Server-side Deal state machine:** Encoded transitions only (§8); deny arbitrary `status` updates from Desk for operational roles; `DISPATCHED` only when linked outward sum equals approved−cancelled; `PARTIALLY_DISPATCHED` when 0 < outward < approved; child table for dispatch/gatepass links with qty.
6. **Alias gate:** Specify statuses illegal while `BUYER_UNRESOLVED`; confirm Customer before party-ledger posting / RECONCILED; alias remap after post = revision + optional re-open exception, never silent Customer overwrite; preserve raw_alias forever (§16).
7. **Fail-closed container close:** Block Settlement close / “fully reconciled” when material exceptions remain open or when inward ≠ outward+remaining (named categories per §27); freeze Settlement snapshot at `closed_at` with `closed_by`; later changes require reopen + new snapshot version (`SETTLEMENT_VALUE_MISMATCH` if drift detected).
8. **Exception typology completeness:** Add or map an explicit validation for lot-not-on-container (not only `LOT_OVERDRAWN`); ensure every §10 rule has a §21 type and a Deal/Container status consequence before coding Phase 1.
